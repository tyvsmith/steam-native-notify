name: add-route
description: Add or change a notification click route under the project's prime rule (mirror Steam, do not invent). Use for "add a route", "change what a click does", "this type should open X", "fix the route for <type>". Walks citation, implementation, catalog prose, table regen, and tests in order.
---

**Mirror Steam, do not invent.** Every invented route in this project's history
was torn out. A route without a Steam citation is forbidden; a click that does
nothing is CORRECT when Steam's own toast does nothing.

All commands run from the repo root.

## 1. Citation first: docs/steam-routing.md

Find (or add, from the bundle) the row for the type in `docs/steam-routing.md`
— the analysis of Steam's shipped UI bundle that every route cites. No row, no
route. If the bundle has to be re-read:
`~/.local/share/Steam/steamui/chunk~*.js`, beautified via
`npx js-beautify -f <chunk> -o chunk.pretty.js`; the quoted strings in the doc
are the stable search keys (minified names reshuffle every Steam build).

## 2. Implement in frontend/routes.ts

- Client types (eSource=1) go in `clientRoute`; server types (eSource=2) in
  `serverRoute`. Return `null` when Steam's own click does nothing.
- Null discipline: missing identity, missing URL template, or a malformed
  field must drop the route to `null`, never emit a broken URL. The tests
  assert this.
- Cite the docs/steam-routing.md row in a comment, matching the existing style.

Decode side, when the rule reads a new field:

- Client field names come from the generated schema
  (`frontend/generated/notifications.ts`, regenerated by `bun run gen` from
  `vendor/*.proto`). **Never guess positionally** — `data.array` is positional
  and shape-guessing misroutes: `FriendInviteRollup.new_invite_count` of 3 once
  became `steam://nav/games/details/3`.
- Server payloads are `body_data` JSON, documented per type in
  docs/steam-routing.md (server catalog, "body fields used").

## 3. Catalog prose: tools/gen-types-table.mjs

Update the type's `CATALOG` entry (the `steam:` and `route:` prose) if the
behaviour description changed. If a new server rule reads body fields, add a
synthesized body to `SYNTH_BODY` (client fields: `SYNTH_FIELD`) — otherwise the
generator derives `null` for the row and fails.

## 4. Regenerate and test

```sh
bun run gen:table    # derives the classification by RUNNING your rule; must pass
```

A `catalog disagrees with routes.ts` error means prose and code differ — fix
whichever is wrong. Commit the regenerated `docs/notification-types.md`.

Add or adjust the **exact-URL** expectation in `tools/test-routes` (full
literal URL; never loosen an existing check), then run the full gate — see the
`offline-validate` skill.

## 5. Live-verify if fireable

If the type has a working test method or server injection, verify on the live
client — see the `live-verify` skill. Cite the observation in the commit.
